## 🎯 About the Project

Many glucose prediction examples treat a patient as a single sensor reading or a static clinical record. Glucosys Twin is an educational and research-oriented prototype that brings those two perspectives together:

- **Static profile:** synthetic EHR attributes such as age, BMI, HbA1c, diabetes status, and medication.
- **Time-varying signals:** synthetic glucose, heart rate, HRV, steps, sleep, and meal-carbohydrate readings at 15-minute intervals.
- **A stateful twin:** temporal features and recent history are used to make a risk prediction and explore simulated alternatives.

The configured target is a glucose rise of **≥40 mg/dL** within the next **2 hours** (eight 15-minute steps). The included datasets are generated by the project; no real patient data is needed for the demo.

The dashboard provides a local interface for reviewing patient profiles, wearable signals, risk predictions, SHAP explanations, intervention recommendations, trajectory forecasts, and model benchmark results.

## ✨ Features

- 📈 **Two-hour spike risk:** predicts the configured glucose-spike target from engineered temporal and profile features.
- 🧑‍⚕️ **Patient twin dashboard:** inspect synthetic patient profiles and replay wearable readings over time.
- 🔍 **Explainable predictions:** view local feature attributions generated with SHAP.
- 🧪 **What-if simulation:** adjust selected inputs and compare the model's output for a simulated state.
- 🚶 **Counterfactual recommendations:** evaluate candidate lifestyle changes, such as walking or carbohydrate moderation, in the simulated twin.
- 📉 **Trajectory projections:** compare baseline and intervention glucose trajectories over the forecast horizon.
- 🧰 **Model comparisons:** view saved precision, recall, F1, ROC-AUC, PR-AUC, and confusion-matrix results.

> Predictions and intervention effects are outputs of a synthetic-data proof of concept; they are not validated health guidance.

## 🚀 Getting Started

### Prerequisites

- **Python 3.10 or newer**
- **Node.js 20.19+ or 22.12+** and npm (required by the Vite 8 frontend)
- Git, if cloning the repository

### Installation

Clone the repository, then open a terminal in its root directory (the directory containing `src/`, `frontend/`, and `requirements.txt`).

#### 1. Set up the Python API

On Windows PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install fastapi "uvicorn[standard]"
```

On macOS or Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install fastapi "uvicorn[standard]"
```

FastAPI and Uvicorn are installed separately because they are imported by the API but are not currently listed in `requirements.txt`.

#### 2. Set up the web dashboard

Open a second terminal in the repository root:

```bash
cd frontend
npm install
```

### Environment Variables

No environment variables are required for the local demo. The frontend currently uses `http://localhost:8000/api` as its API base URL in [`frontend/src/App.jsx`](frontend/src/App.jsx). If you run the API on a different address or port, update that value to match.

The backend reads dataset, model, and prediction settings from [`config/config.yaml`](config/config.yaml). Paths in that file are relative to the repository root.

## 🖥️ Usage

Start the API and dashboard in separate terminals from the repository root.

**Terminal 1 — API**

```bash
python -m uvicorn src.api.main:app --reload --host 127.0.0.1 --port 8000
```

On first startup, if the synthetic EHR/wearable CSVs are missing, the API generates and processes them. If the model metrics artifact is missing, the startup routine trains the models. This may take some time.

**Terminal 2 — frontend**

```bash
cd frontend
npm run dev
```

Open the Vite URL printed in the terminal (normally `http://localhost:5173`). The frontend requests data from the API at `http://localhost:8000/api`.

### API and interactive documentation

When the backend is running:

- Health check: [`http://localhost:8000/api/health`](http://localhost:8000/api/health)
- Interactive Swagger UI: [`http://localhost:8000/docs`](http://localhost:8000/docs)
- Alternative ReDoc view: [`http://localhost:8000/redoc`](http://localhost:8000/redoc)

Example requests:

```bash
# Check API availability
curl http://localhost:8000/api/health

# List synthetic patients
curl http://localhost:8000/api/patients

# Fetch a twin snapshot (replace PAT-001 with a returned patient_id)
curl "http://localhost:8000/api/patients/PAT-001/twin?stream_index=32"

# Fetch saved model metrics
curl http://localhost:8000/api/models/metrics
```

### Generate data and train models manually

The repository includes synthetic CSV data and model artifacts. To regenerate data, rebuild processed features, and retrain the models, run these commands from the repository root with the Python environment activated:

```bash
python -m src.data.generate_synthetic
python -m src.data.process
python -m src.models.train
```

These commands overwrite generated datasets and model artifacts in the configured data and `models/` paths.

### Run tests and frontend checks

```bash
# Python test suite
python -m pytest

# Frontend lint and production build
cd frontend
npm run lint
npm run build
```
